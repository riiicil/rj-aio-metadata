  2. **Visibility Guard & Graceful Reveal (`src/overlay/overlay.js` & `src/overlay/overlay.css`)**:
     - Kept `.rj-hud-wrapper` initially at `opacity: 0 !important; visibility: hidden !important; pointer-events: none !important;`.
     - Attached `linkEl.onload` and `linkEl.onerror` handlers to add `.rj-hud-wrapper.rj-css-ready`, smoothly fading in the HUD once the external stylesheet is completely parsed and applied.

- **Deep Empirical Analysis of 3 User Recordings (`dev-tools/recordings/`)**:
  - Analyzed and compared:
    1. `rekaman-dreamstime (manuallll)-20260930_124753.json`: Manual recording of submitting 3 assets. Revealed true network timings on Dreamstime backend:
       - Save toast (`#noty_layout__bottomRight .noty_bar`) takes 3.7s to 7.7s to appear and 2s to 3s to disappear.
       - Submit toast (`#noty_layout__bottomRight .noty_bar`) takes 4.8s to 6.4s to appear.
       - Dreamstime AJAX modal replacement: the new asset modal (`#js-editcontainer > div.popup-upload`) is inserted 1.3s to 1.8s *after* the submit toast appears.
    2. `rekaman-dreamstime (save only ext)-20260930_124406.json`: Extension running Save Only mode. Worked smoothly because `#js-next-submit` (chevron arrow) was clicked, which directly and immediately navigates the carousel modal.
    3. `rekaman-dreamstime (submit imm ext)-20260930_124544.json`: Extension running Submit Immediately mode. Showed submit was clicked only ~300ms after save, and the extension gave up after only 250ms, while the actual new asset modal arrived 4.5 seconds later (at t=19101ms).
- **Two Critical Root Causes Diagnosed & Resolved**:
  1. **`#js-submit-message` Selector Bypass (`DreamstimeAdapter.js`)**:
     - Both `saveDraft()` and `submitForReview()` queried `#js-submit-message:not([style*="none"])`.
     - In Dreamstime, `#js-submit-message` is permanently rendered inside the modal with `data-state="hidden"` and an *empty* `style` attribute.
     - Therefore, `:not([style*="none"])` matched it immediately on tick 1 (at 0ms), falsely treating it as an already-appeared toast.
     - Stage 2 then queried `.noty_bar`, which was `null` (since the server response takes 3-7s), causing Stage 2 to break out immediately in 0ms!
     - As a result, both `saveDraft()` and `submitForReview()` exited instantaneously without waiting for either server toast, triggering overlapping AJAX requests and clicking submit in ~300ms.
     - **Fix**: Completely removed `#js-submit-message` from the toast query in both `saveDraft()` and `submitForReview()`. Both methods now strictly poll `#noty_layout__bottomRight .noty_bar, .noty_bar` for actual text content (`saved`/`success` for draft, `submitted`/`success`/`id:` for submit) with an expanded 12000ms appearance timeout and 10000ms disappearance timeout, followed by lingering node purge and 400ms settling buffer.
  2. **1.2s - 2.5s Transient DOM Unmount Window in `handlePostSubmitTransition()`**:
     - Dreamstime submits via AJAX: it removes the current modal (`$('#<id>').remove()`) from `#js-editcontainer`, sends the submit request, and inserts the new modal HTML into `#js-editcontainer` 1.2s to 2.5s later.
     - `handlePostSubmitTransition()` previously checked `if (!modalActive) return { done: true }` immediately on tick 1 (at 250ms), mistaking the normal transient unmount gap for batch completion!
     - It logged `"Edit modal closed after submission. All assets completed."` and stopped the loop after asset 1, resetting state to idle and causing the user to have to click Start repeatedly.
     - **Fix**: Removed the immediate modal absence check at the start and inside the polling loop. The method now actively polls up to 15000ms specifically for `candId && candId !== submittedAssetId`, evaluates carousel loop-back completion (`this.processedAssetIds.has(nextId) || nextId === this.firstAssetId`), detects cross-page redirects via `window.__rj_is_unloading`, and only confirms batch completion if the modal remains truly absent after the entire 15s polling window expires.
- **Accurate Asset Progress Tracking in `AutomationOrchestrator.js`**:
  - In Dreamstime's dynamic while loop, added `processedCount++; this.processedCount = processedCount;` after asset completion so the HUD progress counter and completion banner accurately report completed assets (e.g. "Finished 3 assets" instead of 0 or 1).
- **CSP Console Warning Elimination in `dom_helpers.js`**:
  - In `simulateClick`, temporarily removed `href` on `javascript:` links during `element.dispatchEvent(clickEvt)` and restored it in `finally`, eliminating the browser CSP console violation warning while allowing all click handlers to fire.

## Session Entry 1 — Dreamstime Mode B Submission Auto-Transition & Toast Race Condition Resolution

**Time:** ~12:05 WIB<br>
**Branch:** `task/dreamstime-mode-b-submit-fix`<br>
**Commit:** `8e5268c` (`fix(dreamstime): decouple mode b submission auto-transition and resolve toast race condition`)<br>
**Product code changed:** YES<br>
**Pushed:** NO

### What Was Done
- **Mode B Navigation Decoupling (`src/overlay/AutomationOrchestrator.js`)**:
  - Investigated issue reported by user where Mode B ("Submit Immediately") ceased progressing after the first asset and falsely marked automation as completed / finished.
  - Identified root cause: In Dreamstime, clicking `#submitbutton` automatically submits the file and advances the editor modal to the next unfinished asset (or closes the modal if the queue is empty). The orchestrator previously executed `adapter.saveDraft()`, followed by `adapter.submitForReview()`, and then unconditionally executed `adapter.navigateToNext()`.
  - When `navigateToNext()` was called in Mode B, it read the newly loaded asset ID, added it to `processedAssetIds`, and clicked the next arrow a second time—skipping assets or tripping the Infinite Carousel Guard (`processedAssetIds.has(nextId) === true`), terminating the loop after 1 asset.
  - Decoupled Mode A vs Mode B navigation in `AutomationOrchestrator.js`: Mode B now delegates post-submission progression to `adapter.handlePostSubmitTransition(currentId)` while Mode A retains standard carousel navigation via `adapter.navigateToNext()`.
- **Dreamstime Post-Submit Auto-Transition Handler (`src/adapters/DreamstimeAdapter.js`)**:
  - Implemented `handlePostSubmitTransition(submittedAssetId)`:
    - Registers `submittedAssetId` into `this.processedAssetIds`.
    - Checks if the edit modal closed immediately upon submission (`!modalActive`), cleanly returning `{ done: true, nextAssetId: null }` when all assets in the batch are finished.
    - Polls up to 5000ms for the modal to display the next asset ID (`candId && candId !== submittedAssetId`).
    - Provides fallback next-arrow clicking only if Dreamstime auto-advance does not trigger within the timeout period.
    - Returns `{ done: false, nextAssetId }` when the next asset is ready, allowing the orchestrator loop to seamlessly proceed to the next item.
- **Save and Submit Toast Race Condition Resolution (`src/adapters/DreamstimeAdapter.js`)**:
  - Investigated race condition where `submitForReview()` immediately caught lingering `.noty_bar` DOM nodes from the preceding `saveDraft()`, exiting immediately before server submission confirmation.
  - Updated `saveDraft()` to purge lingering `.noty_bar` elements once the close animation completes.
  - Added pre-submit cleanup in `submitForReview()` to clear stale `.noty_bar` elements before clicking the submit button, ensuring the toast watcher only detects the newly spawned submit notification.
