## Session Entry 1 — Multi-Tab Automation State Isolation & Auto-Heal Stabilization

**Time:** ~21:25 WIB<br>
**Branch:** `task/e2e-hardening-polish`<br>
**Commit:** `cdeb90d` (`fix(overlay): isolate automation state per platform and scope auto-heal by tab ID`)<br>
**Product code changed:** YES<br>
**Pushed:** NO

### What Was Done
- **Root Cause Diagnosis of Multi-Tab Glitch & Browser Freeze (*Not Responding*):**
  1. *Cross-Tab Blind Storage Broadcasting*:
     - When starting automation on Tab 1 (e.g. Adobe Stock), `rj_automation_state: { isRunning: true, platformId: 'adobestock' }` was broadcast across all open browser tabs.
     - `OverlayHUD.onStorageChanged` in `src/overlay/overlay.js` failed to filter incoming events by `platformId`.
     - Inactive tabs on other platforms (e.g. Tab 2 Dreamstime) incorrectly assumed the start signal was addressed to them and invoked `this.startAutomation()` concurrently in the background.
  2. *Cross-Tab Storage Ping-Pong Conflict Loop*:
     - The accidentally triggered secondary tab inspected its page, found 0 asset cards or an unmounted edit modal, and executed its idle exit sequence (`if (total === 0)`), writing `rj_automation_state: { isRunning: false, status: 'idle' }` to storage.
     - Tab 1 received this external idle signal, forcing an immediate abort (`this.stopAutomation(true)`).
     - Concurrent asynchronous card processing loops in Tab 1 updated the badge to "Generating..." while the stop signal forced it to "Stopped", producing rapid UI flickering and thrashed the browser event loop into high CPU lockup (*Not Responding*).
  3. *Unscoped Background Tab Event Listener*:
     - `chrome.tabs.onUpdated` in `src/background/service_worker.js` blindly listened to any tab loading in Chromium without checking whether that tab was the active runner tab. Loading or reloading unrelated tabs automatically wiped the active automation state.
  4. *Missing `isProcessing` Orchestrator Getter*:
     - `restoreAutomationState` in `overlay.js` checked `!this.orchestrator?.isProcessing`. Because `isProcessing` was undefined on the class, any new tab mounting or reloading auto-healed and killed active automation runs.
- **Architectural Implementation:**
  1. *Per-Platform Storage Scoping (`src/overlay/overlay.js`)*:
     - In `onStorageChanged`, added a strict guard: `if (state.platformId && state.platformId !== this.platformId) return;`.
     - In `restoreAutomationState`, ensured newly mounted HUD instances only auto-heal states matching their own platform or global resets.
     - In constructor, added `this.tabId = null` and requested sender tab ID on `init()`.
  2. *Centralized Orchestrator State Sync (`src/overlay/AutomationOrchestrator.js`)*:
     - Added `isProcessing` getter returning `Boolean(this.hud?.isAutomationRunning || this.isCardProcessing)`.
     - Created `_setAutomationState(patch)` helper that automatically includes `platformId` and `tabId`.
     - Replaced all raw `chrome.storage.local.set` calls in start, loop completion, catch, finally, and stop methods with `_setAutomationState`.
  3. *Scoped Background Auto-Heal & Tab Lifecycle Tracking (`src/background/service_worker.js`)*:
     - Added `GET_SENDER_TAB_ID` runtime message handler returning `sender.tab?.id`.
     - Updated `resetAutomationState(platformId = null)` to preserve target platform context.
     - Scoped `chrome.tabs.onUpdated` to strictly auto-heal only when the reloading tab ID matches `state.tabId` (`state.tabId === tabId`), with URL fallback.
     - Added `chrome.tabs.onRemoved` listener to cleanly auto-heal if the runner tab is closed.
  4. *Targeted Tab Verification in Popup (`src/popup/popup.js`)*:
     - In `DOMContentLoaded`, pings `state.tabId || activeTab.id` so opening the popup while focused on a different tab does not falsely auto-heal a background runner tab.
